### 防范原则

1. **禁止凭记忆断言数值**：所有数值必须 Grep 验证
2. **禁止凭便利硬编码**：所有 UI 文案必须从 `data.js` 读取
3. **禁止凭旧版记忆**：项目版本迭代频繁，必须以当前代码为准
4. **禁止凭印象写文案**：技能描述必须以 `case` 分支数值为准

## 四、模式观察（用户行为模式，主动适应）

### 用户沟通模式
- 期望 AI 主动发现问题，不等用户提醒
- 期望 AI 主动对标市面大游戏调整 UI
- 期望 AI 建立长效机制而非临时修复
- 偏好简洁直接的表达，不喜欢冗长解释

### 用户关注重点（按频次）
1. **前端动态化**（最高频）：UI 文案必须从数据读取
2. **UI 审美**：要超越市面大游戏水准
3. **自我学习**：AI 要主动纠错与进化
4. **平衡性**：所有角色都要可玩，不能太难杀
5. **完整性**：新增内容必须同步到所有引用点
6. **业务逻辑**：技能必须真正生效，不能空实现

### 用户不满触发点
- AI 重复犯同类错误（已建立模式识别机制）
- AI 凭记忆断言而非验证（已建立三重校验）
- AI 不主动发现问题（已建立预防性扫描）
- UI 退步或缺乏设计感（已建立审美对标库）
- 文档与代码不同步（已建立十项同步清单）

## 五、入档规则

### 入档触发器

AI 在以下场景检测到用户反馈时，**立即入档**：

1. 用户使用强约束词：「必须」「不能」「禁止」「每次都要」
2. 用户使用复发提示词：「不要再」「每次都忘了」「总是」
3. 用户表达偏好：「喜欢」「偏好」「像 XX 一样」
4. 用户表达不满：「不对」「太丑」「不满意」
5. 用户纠正 AI：「不是这样」「应该是」「错了」
6. 用户提出 AI 未考虑的边界情况

### 入档流程

```
检测到反馈
    ↓
分类：显式约束 / 偏好 / 纠正 / 模式
    ↓
追加到对应章节（表格末尾）
    ↓
判断是否需要升级为硬约束
    ├─ 是 → 同步到 硬性约束.md / docs/HARD_CONSTRAINTS.md
    └─ 否 → 仅入档本文件
    ↓
在 项目修改记录.md 标注「反馈吸收」
    ↓
更新 SELF_LEARNING 指标（反馈吸收数 +1）
```

### 入档规范

- 每条反馈必须包含：日期、原始内容、入档位置、触发场景
- 纠正类必须包含：AI 判断、用户纠正、根因、防范
- 同类反馈可合并，但必须保留所有出现日期
- 反馈被覆盖时，旧条目标注「已被 YYYY-MM-DD 反馈覆盖」而非删除
