# 变更流程规范

> **A级流程** — 超级大厂标准，防止幻觉与错漏。
> 任何代码变更必须按此流程执行。

## 📐 变更分级

| 级别 | 定义 | 流程 | 示例 |
|------|------|------|------|
| **S级** | 重大架构/系统重构 | 完整流程（spec→tasks→checklist→实现→审查→文档）| 模块拆分、新增子系统 |
| **A级** | 新增角色/技能/机制 | spec + 实现 + 全量检查 | 新增通天教主、诛仙剑阵重构 |
| **B级** | 修复bug/调整数值 | 实现 + 关联检查 + 记录 | 修复被动显示、调整炮攻击力 |
| **C级** | 文案/UI微调 | 实现 + 记录 | 改技能描述、调整颜色 |

---

## 🔄 标准变更流程（S/A级）

### Phase 1: 需求理解（理解阶段）

#### 1.1 需求复述
- 用自己的话复述用户需求
- 列出所有显性要求
- 识别所有隐含要求（风格/约束/关联）

#### 1.2 约束匹配
- 检查 [[HARD_CONSTRAINTS]] 是否有相关约束
- 检查用户历史提醒是否有相关要求
- 检查 [[SKILL_RAG]] 是否有匹配的技能模式

#### 1.3 现状调研
- 阅读相关代码（完整上下文，非片段）
- `grep -rn` 扫描所有关联位置
- 记录当前实现与描述的差异

#### 1.4 设计决策
- 机制合理性审查（是否符合游戏框架）
- 数值边界测试（0%/50%/100%等极端值）
- 描述风格审查（古文/不提他人等）
- UI显示审查（动态显示/无硬编码）

### Phase 2: 规格创建（S/A级必须）

在 `.trae/specs/<version>/` 创建：

#### spec.md
```markdown
# <版本号> — <简述>

## Why（为什么改）
<用户原话 + 背景>

## What Changes（改什么）
- 变更点1
- 变更点2

## Impact（影响范围）
- 文件1：xxx
- 文件2：xxx

## Scenarios（验证场景）
- 场景1：xxx
- 场景2：xxx
```

#### tasks.md
```markdown
# 任务分解

- [ ] T1: xxx
- [ ] T2: xxx
```

#### checklist.md
```markdown
# 验证清单

- [ ] node -c 通过
- [ ] 描述与实现一致
- [ ] ...
```

### Phase 3: 实现（执行阶段）

#### 3.1 实现原则
- **单一职责** — 每次改动只做一件事
- **最小变更** — 只改必要的部分
- **不破坏现有** — 保持向后兼容（除非明确删除）

#### 3.2 关联扫描（强制）
修改任何代码后，必须 `grep -rn` 扫描：
- 修改的函数名/变量名
- 修改的技能id/buff类型
- 修改的UI文案

#### 3.3 多模式适配
- PVE 模式验证
- PVP 模式验证
- 三英模式验证
- 故事模式验证

### Phase 4: 审查（验证阶段）

按 [[ANTI_HALLUCINATION]] 清单逐项检查：

- [ ] 描述与实现一致性
- [ ] 全局影响检查
- [ ] 多模式适配
- [ ] 数据流完整性
- [ ] 语法校验
- [ ] 文档同步

### Phase 5: 文档同步（收尾阶段）

- [ ] 更新 `项目修改记录.md`（最新置顶）
- [ ] 更新 [[HARD_CONSTRAINTS]]（如有新约束）
- [ ] 更新 [[SKILL_RAG]]（如涉及技能）
- [ ] 更新 [[BUFF_SYSTEM]]（如涉及buff）
- [ ] 更新 [[ARCHITECTURE]]（如涉及架构）
- [ ] 资源版本号 `?v=N` 递增

## 🐛 Bug修复流程（B级）

### 1. 复现与定位
- 明确复现步骤
- 定位根因（不是表象）

### 2. 根因分析
- 为什么会发生？
- 是否有同类问题？
- 是否是设计缺陷？

### 3. 修复
- 最小化修复（不扩大改动范围）
- 修复后检查关联位置

### 4. 验证
- 原bug不再复现
- 无新增bug
- 多模式验证

### 5. 记录
- 在 `项目修改记录.md` 记录根因与修复

## 📝 文案变更流程（C级）

### 1. 风格审查
- 古文风格？（通天教主等金仙角色）
- 不提及其他角色？
- 用词符合角色身份？

### 2. 关联检查
- 描述与代码数值是否一致
- UI显示是否需要同步更新
- 教程/codex页面是否需要同步

### 3. 记录
- 简要记录变更

## 🧹 文档维护流程

### 项目修改记录.md 维护

#### 原则
1. **最新置顶** — 新版本在上，旧版本在下
2. **过时清理** — 超过3个版本的旧记录可归档到 `docs/archive/`
3. **精简记录** — 只记核心变更，不记细节（细节在spec中）

#### 格式
```markdown
## v<版本号>-<简述> · <标题>

### 用户反馈
> <用户原话>

### 核心修改
- 变更点1
- 变更点2

### 关键代码位置
| 文件 | 行号 | 内容 |

### 验证
- node -c 通过
- ?v=N 递增
```

### 文档归档规则
- 超过3个版本的旧 `项目修改记录.md` 条目 → 归档到 `docs/archive/changelog-v<起>-v<止>.md`
- 过时的 spec → 归档到 `docs/archive/specs/`
- 文档每季度审查一次，删除过时内容

## 🤖 AI协作提示词工程

### 需求意图匹配

当用户提出需求时，AI应自动匹配：

| 用户关键词 | 匹配文档 | 匹配技能模式 |
|-----------|---------|-------------|
| 技能/主动/被动 | [[SKILL_RAG]] | 查RAG注册表 |
| buff/状态 | [[BUFF_SYSTEM]] | buff类型映射 |
| 角色/属性 | [[CHARACTER_REGISTRY]] | 角色约束 |
| bug/修复 | [[ANTI_HALLUCINATION]] | 审查清单 |
| 重构/模块 | [[ARCHITECTURE]] | 模块边界 |
| 数值/平衡 | [[HARD_CONSTRAINTS]] | 平衡约束 |

### 智能匹配流程

1. **提取关键词** — 从用户需求中提取核心概念
2. **查询RAG** — 在 [[SKILL_RAG]] 中匹配技能模式
3. **加载约束** — 从 [[HARD_CONSTRAINTS]] 加载相关约束
4. **检查清单** — 从 [[ANTI_HALLUCINATION]] 加载检查项
5. **确认方向** — 如有歧义，用 AskUserQuestion 确认
6. **执行变更** — 按标准流程执行

### 防幻觉三重校验

1. **前置校验** — 改动前确认理解正确
2. **过程校验** — 改动中检查关联影响
3. **后置校验** — 改动后按清单验证
