# SELF_LEARNING.md — AI 自我学习与持续改进机制

> 本文件建立 AI 代理在「博弈之王（中国象棋）」项目中长期生效的自我学习闭环。
> 所有 AI 代理在每次写入操作后 **必须** 遍历项目具体信息进行自动纠错，防止幻觉累积。
> 本文档为机制规范，不含实现代码。
>
> **v37 增强**：从「被动纠错」升级为「主动学习 + 自适应进化 + 反馈吸收」三阶模型。
> - 会话启动时主动回顾历史教训（防止同类错误复发）
> - 从错误模式中自动进化新规则（无需用户提醒）
> - 主动吸收用户反馈并固化为约束（用户说一次即入档）
> - 量化学习指标衡量改进效果（可视化自我评估）

---

## 〇、三阶学习模型（v37 新增）

自我学习从单次 PDCA 升级为「学习 → 应用 → 进化」三阶：

```
┌──────────────────────────────────────────────────────────────┐
│  阶段一：学习（Before）— 会话启动 / 任务接收                  │
│  - 读取 RAG 教训库                                            │
│  - 读取近 7 天项目修改记录                                    │
│  - 读取用户反馈档案（docs/USER_FEEDBACK.md）                  │
│  - 读取本会话相关主题的归档教训                                │
├──────────────────────────────────────────────────────────────┤
│  阶段二：应用（During）— 任务执行                            │
│  - PDCA 闭环（Plan → Do → Check → Act）                      │
│  - 实时幻觉检测                                               │
│  - 主动审查触发器                                             │
│  - 预防性扫描（在用户提问前主动发现问题）                     │
├──────────────────────────────────────────────────────────────┤
│  阶段三：进化（After）— 任务完成                              │
│  - 重复错误模式识别（≥2 次同类错误 → 自动生成新规则）        │
│  - 用户反馈提取规则化（用户意见 → 入档为约束）               │
│  - 学习指标更新（错误率、复发率、覆盖率）                     │
│  - 跨会话知识传递（教训归档到 docs/archive/）                │
└──────────────────────────────────────────────────────────────┘
```

## 一、自我学习闭环模型

建立 PDCA 闭环，贯穿每次代码与文档变更：

### Plan（计划 · 修改前）
- **扫描相关代码**：使用 Grep / Glob / SearchCodebase 定位待修改符号在全部文件中的引用点
- **扫描相关文档**：检查 `docs/`、`AGENTS.md`、`.trae/specs/` 中对该符号的描述
- **扫描历史教训**：读取 `docs/SKILL_RAG.md` 的「教训」章节，确认本次修改不重蹈覆辙
- **声明修改意图**：在内部记录本次 Plan 的预期变更范围（哪些文件、哪些数值、哪些文档）

### Do（执行 · 修改中）
- **单一数据源原则**：数值与配置只在一处定义（`js/data.js` 为权威源），其他位置只能引用
- **数据驱动渲染**：UI 必须动态读取数据，禁止在 HTML / 渲染函数中硬编码具体数值
- **同步修改**：代码、文档、数值三方在一次 Do 阶段内同步完成，不得留待「下次再补」
- **最小变更**：只修改与目标直接相关的行，不顺手重构无关代码

### Check（检查 · 修改后）
- **代码遍历校验**：`node -c` 校验所有改动过的 JS 文件
- **文档同步校验**：对照「十项同步清单」逐项核验
- **数值反向校验**：文档中声称的数值，必须用 Grep 在代码中反向验证存在且一致
- **幻觉检测**：若文档声称「已修改 X」但代码中 X 未变，立即判定为幻觉并触发 Act

### Act（处置 · 闭环）
- **立即纠错**：发现幻觉或不一致，在同一会话内修复，不留尾巴
- **更新 RAG**：将根因与防范措施写入 `docs/SKILL_RAG.md` 的「教训」章节
- **更新约束**：若发现新型违规模式，扩充 `docs/HARD_CONSTRAINTS.md`
- **更新修改记录**：在 `项目修改记录.md` 中追加本次变更条目并标注时间戳

## 二、自我纠错触发器

AI 在以下场景 **必须自动触发** 纠错（不等用户提醒）：

1. **幻觉检测**：文档声称已修改 X，但代码实际未变
   - 触发动作：Grep 验证 → 修正代码或撤回文档声明 → 记录到 RAG

2. **同步检测**：代码数值与文档描述不一致
   - 触发动作：以代码为权威源，同步文档；若文档为需求源，反向修正代码

3. **硬编码检测**：HTML / 渲染函数中出现具体数字而非动态读取
   - 触发动作：替换为对 `data.js` / `PIECE_STATS` / 角色对象的引用

4. **描述检测**：技能描述文案与 `skills.js` 的 `case` 分支数值不符
   - 触发动作：以 `case` 分支为权威，同步 `data.js` 中 `skill.desc` 与 `actives[].desc`

5. **完整性检测**：新增角色后未同步故事章节（`data.js` 的 STORY_CHAPTERS）
   - 触发动作：补全章节解锁逻辑、选将池、阵营归属

6. **一致性检测**：修改 `PIECE_STATS` 后未同步新手指南 / 平衡文档
   - 触发动作：扫描 `docs/` 与 `设计文档*.md` 中对旧数值的引用并同步

7. **双向同步检测**：修改技能 CD 后未同步技能描述
   - 触发动作：检查 `skill.cd` / `actives[].cd` 与对应 `desc` 文案中的 CD 数字

## 三、变更后自动扫描流程

每次代码变更后，AI **必须** 自动按序执行以下五步：

1. **语法校验**
   - 执行 `node -c` 校验所有修改过的 JS 文件
   - 命令模板：
     ```
     node -c js/data.js && node -c js/engine.js && node -c js/skills.js && \
     node -c js/portrait.js && node -c js/audio.js && node -c game.js
     ```
   - 任一文件失败立即停止后续步骤并修复

2. **数值反向校验**
   - 提取本次变更涉及的数值
   - 在 `docs/`、`设计文档*.md`、`项目修改记录.md` 中搜索该数值
   - 凡文档声称值与代码实际值不一致，立即修正文档

3. **文档同步校验（十项同步清单）**
   - [ ] `PIECE_STATS` 与新手指南数值一致
   - [ ] 角色属性（atk/def/int）与角色描述一致
   - [ ] 技能 CD 与技能描述文案一致
   - [ ] 技能伤害公式与 `calcDamage` 实现一致
   - [ ] 兵种相克规则与文档描述一致
   - [ ] 阵营归属与阵营模式说明一致
   - [ ] 故事章节解锁角色与选将池一致
   - [ ] AI 难度描述与 B王思考深度一致
   - [ ] HP/atk/def 数值范围与平衡基线表一致
   - [ ] 被动技能触发类型与 `skills.js` case 分支一致

4. **硬编码扫描**
   - Grep 扫描 `index.html`、`game.js` 渲染函数中的数字字面量
   - 排除：循环索引、坐标常量、画布尺寸、颜色值
   - 命中具体数值（HP/atk/def/CD 等）即标记为待动态化

5. **完整性校验**
   - 新增角色：是否同步到 STORY_CHAPTERS、选将池、阵营、`docs/`、`项目修改记录.md`
   - 新增章节：是否同步到故事模式入口、解锁条件
   - 新增技能：是否同步到 `skills.js` 的 case 分支、技能描述、RAG 教训
   - 新增机制：是否同步到 `HARD_CONSTRAINTS.md`、`AGENTS.md` 硬约束

## 四、RAG 持续更新机制

RAG（检索增强记忆）通过 `docs/SKILL_RAG.md` 持续累积项目知识：

### 触发场景与写入位置

| 事件类型 | 写入目标 | 写入内容 |
|---------|---------|---------|
| 修复 bug | `SKILL_RAG.md` 「教训」章节 | 根因、现象、修复方法、防范措施 |
| 平衡性调整 | `SKILL_RAG.md` 「平衡基线表」 | 调整前后数值、理由、影响角色 |
| 新增机制 | `HARD_CONSTRAINTS.md` 约束表 | 约束名称、规则、违反后果 |
| 新增角色 | `SKILL_RAG.md` 「角色档案」 | 角色定位、技能联动、平衡建议 |
| 新增教训模式 | 本文档第二章触发器列表 | 新增触发器条目 |

### 归档机制
- 每月 1 日（或当 `SKILL_RAG.md` 超过 500 行时）将历史条目归档到 `docs/archive/YYYY-MM/`
- 归档后 `SKILL_RAG.md` 仅保留近 30 天活跃条目 + 指向归档的索引
- 归档目录结构：`docs/archive/YYYY-MM/SKILL_RAG.history.md`

### 写入规范
- 每条教训必须包含：`日期 / 触发场景 / 根因 / 防范 / 引用文件`
- 数值类条目必须附带代码行号或符号名，便于反向定位
- 禁止写入模糊描述（如「注意同步」），必须给出可执行检查项

## 五、幻觉防御机制

### 三重校验
1. **前置校验（修改前）**：Grep 确认待修改符号在代码中的真实状态，禁止凭记忆断言
2. **过程校验（修改中）**：每次 Edit 后立即 Read 验证改动落地，确认 old_string / new_string 精确匹配
3. **后置校验（修改后）**：修改声明中提到的每个事实，必须用 Grep 在代码中找到对应证据

### 反向验证
- 文档中出现的任何「已修改 X 为 Y」「X 当前值为 Y」声明，必须用 Grep 在代码中验证
- 找不到对应代码证据的声明，判定为幻觉，立即撤回或修正
- 验证范围包括：`js/*.js`、`game.js`、`index.html`、`docs/*.md`

### 交叉验证
- 同一数值在多文件中出现时，必须全部一致：
  - `PIECE_STATS` ↔ 新手指南 ↔ 设计文档
  - `skill.cd` ↔ `skill.desc` ↔ 技能列表 UI
  - 角色属性 ↔ 角色描述 ↔ 选将屏显示
- 任一文件与其他文件不一致，以代码权威源为准同步其余文件

### 时间戳机制
- 每次修改后在 `项目修改记录.md` 追加条目，格式：
  ```
  ## YYYY-MM-DD HH:MM | 版本号 | 简述
  - 修改文件：...
  - 修改内容：...
  - 校验结果：node -c 通过 / 文档同步 N 项 / 硬编码扫描 N 项
  ```
- 时间戳取本地时区 `Asia/Shanghai`

## 六、学习优先级矩阵

按严重程度划分处理优先级，AI 必须按矩阵顺序处置：

| 级别 | 定义 | 处置时限 | 示例 |
|------|------|---------|------|
| **P0** | 导致 bug、错误信息、崩溃 | 立即修复，同会话内完成 | 炮自杀、AI 移动失败、点击无响应 |
| **P1** | 维护成本高、文档/代码不同步 | 当次会话内修复 | 数值不一致、技能描述与实现不符、硬编码 |
| **P2** | 风格不一致、注释过时 | 下次相关改动时顺手修复 | 命名不规范、注释指向已删除代码 |
| **P3** | 历史记录、合理保留 | 不处理 | 早期设计文档、已废弃但保留的注释 |

### 处置原则
- P0 必须在用户感知前由 AI 自行发现并修复
- P1 必须在本次任务结束前修复，不得遗留到下次
- P2 记录到 `SKILL_RAG.md` 待办区，下次触碰相关代码时一并修复
- P3 仅在用户明确要求时处理

## 七、主动维护清单

AI 应 **主动**（不等用户提醒）维护以下场景：

1. **发现硬编码时主动动态化**
   - 扫描命中具体数值 → 替换为对 `data.js` 常量的引用 → 同步文档

2. **发现文档不同步时主动同步**
   - 反向校验命中不一致 → 以代码为权威源 → 修正文档数值与描述

3. **发现 UI 不符合审美清单时主动调整**
   - 对照水墨主题规范 → 调整配色/间距/字号 → 不引入新框架

4. **发现技能描述与实现不符时主动同步**
   - Grep `case` 分支数值 → 比对 `skill.desc` / `actives[].desc` → 同步文案

5. **发现新增内容未同步到所有引用点时主动补全**
   - 新增角色 → 检查 STORY_CHAPTERS / 选将池 / 阵营 / 文档 / 修改记录
   - 新增技能 → 检查 case 分支 / 描述 / RAG 教训
   - 新增机制 → 检查 HARD_CONSTRAINTS / AGENTS.md 硬约束

### 主动维护边界
- 主动维护仅限「同步」「纠错」「补全」，不得借机重构或新增功能
- 涉及数值平衡的主动调整必须先记录到 RAG 待办，由用户确认后再执行
- 主动维护产生的改动同样需要走 PDCA 闭环与时间戳记录

## 八、会话启动回顾机制（v37 新增）

AI 在 **每次会话启动 / 接收新任务时**，必须主动执行「学习阶段」回顾，避免重蹈历史覆辙。

### 强制回顾清单

按以下顺序读取，**不等用户提醒**：

1. **读取 RAG 教训库**
   - 文件：`docs/SKILL_RAG.md` 的「教训」章节
   - 目标：识别近 30 天的高频错误模式
   - 行动：在本次任务执行前，确认不重蹈覆辙

2. **读取近 7 天项目修改记录**
   - 文件：`项目修改记录.md` 末尾 7 天章节
   - 目标：了解近期变更、未解决问题、用户关注点
   - 行动：若本次任务与近期变更相关，优先延续上下文

3. **读取用户反馈档案**
   - 文件：`docs/USER_FEEDBACK.md`（不存在则跳过）
   - 目标：提取用户已表达过的偏好、禁令、强约束
   - 行动：将用户反馈作为隐式约束纳入本次任务

4. **读取归档教训（按主题匹配）**
   - 目录：`docs/archive/YYYY-MM/`
   - 目标：定位与本次任务主题相关的历史教训
   - 行动：若命中相关教训，在本次任务执行时主动应用防范措施

5. **读取硬约束最新版**
   - 文件：`硬性约束.md`、`AGENTS.md`、`docs/HARD_CONSTRAINTS.md`
   - 目标：确认本次任务方向不违反任何硬约束
   - 行动：若发现潜在冲突，先与用户确认方向

### 回顾触发条件

- 新会话首次接收用户任务
- 同一会话内任务主题切换（如从「技能调整」切到「UI 优化」）
- 用户提到与近期修改相关的内容
- 修改影响范围 ≥ 3 个文件

### 回顾产物

回顾完成后，AI 应在内部记录：
- 本次任务相关的历史教训条目数
- 适用的高频错误模式清单
- 需要主动避免的复发点
- 用户隐式约束清单

## 九、自适应规则进化（v37 新增）

AI 从错误模式中**自动进化新规则**，无需用户提醒。

### 进化触发条件

满足以下任一条件即触发规则进化：

1. **同类错误复发 ≥ 2 次**
   - 例如：硬编码问题在两次不同修改中均出现 → 自动升级为强约束

2. **用户就同一类问题提醒 ≥ 2 次**
   - 例如：用户两次提到「UI 文案与数据不同步」→ 自动生成同步规则

3. **发现新型违规模式**
   - 例如：首次出现「技能描述用错对象」（角色而非棋子）→ 生成新约束

4. **幻觉模式重复**
   - 例如：两次声称「已修改 X」但 X 未变 → 强化前置校验

### 进化流程

```
检测到错误模式
    ↓
分类：硬编码 / 幻觉 / 不同步 / 描述错误 / 完整性缺失 / 新模式
    ↓
检索现有规则库（HARD_CONSTRAINTS / SELF_LEARNING / UI_SELF_AUDIT）
    ↓
是否已有规则覆盖？
    ├─ 是 → 强化已有规则（增加触发条件或处罚条款）
    └─ 否 → 生成新规则草案
                ↓
          写入对应文档：
            - 通用约束 → 硬性约束.md
            - UI 约束 → docs/UI_SELF_AUDIT.md
            - 自我学习 → 本文档第二章触发器
            - 技能约束 → docs/SKILL_RAG.md
                ↓
          在 项目修改记录.md 中标注「规则进化」
                ↓
          更新 SELF_LEARNING 指标（规则数 +1）
```

### 规则进化示例

**示例 1**：用户两次提到「B王主动技能数与实际不符」
- 检测：硬编码复发
- 进化：在 `硬性约束.md` 第十四·二节增加显式条目
- 新规则：所有 B王技能数描述必须从 `CHARACTERS.bking.actives.length` 读取

**示例 2**：两次发现「技能 case 分支数值与 desc 不符」
- 检测：描述检测复发
- 进化：在本文档第二章触发器 #4 强化
- 新规则：每次修改 `skills.js` case 分支后，强制同步 `data.js` 中对应 `desc`，并在 PR 描述中列出修改的 desc 清单

### 进化记录

每次规则进化必须在 `项目修改记录.md` 中追加条目：

```
## YYYY-MM-DD | vN-rule-evolution | 规则进化
- 触发：[错误模式描述]
- 根因：[根因分析]
- 进化：[新规则或强化规则内容]
- 写入位置：[目标文档路径与章节]
- 指标更新：规则总数 N → N+1
```

## 十、用户反馈学习机制（v37 新增）

主动吸收用户反馈并**固化为持久约束**，用户说一次即入档。

### 反馈识别触发器

AI 在以下场景检测到用户反馈时，自动进入反馈吸收流程：

1. **显式约束类**
   - 用户使用「必须」「不能」「禁止」「每次都要」等强约束词
   - 用户使用「不要再」「每次都忘了」「总是」等复发提示词
   - 用户给出明确的偏好（如「保存按钮放底部」）

2. **隐性偏好类**
   - 用户对某次结果表达「不满意」「太丑」「不对」
   - 用户多次要求同类调整（如「再大点」「再小点」）
   - 用户对比其他产品（如「像 XX 一样」）

3. **纠正类**
   - 用户指出 AI 的错误判断
   - 用户撤回 AI 的修改
   - 用户提出 AI 未考虑的边界情况

### 反馈吸收流程

```
检测到用户反馈
    ↓
分类：硬约束 / 偏好 / 纠正 / 模式
    ↓
判断是否已存在对应规则
    ├─ 已存在 → 强化或细化已有规则
    └─ 不存在 → 创建新规则草案
                ↓
          写入对应文档：
            - 项目级硬约束 → 硬性约束.md / AGENTS.md
            - 用户偏好 → docs/USER_FEEDBACK.md
            - UI 偏好 → docs/UI_SELF_AUDIT.md
            - 自我学习 → 本文档
                ↓
          在 项目修改记录.md 中标注「反馈吸收」
                ↓
          更新 SELF_LEARNING 指标（反馈吸收数 +1）
```

### 反馈档案维护

`docs/USER_FEEDBACK.md`（不存在时由 AI 首次反馈触发创建）结构：

```markdown
# 用户反馈档案

## 一、显式约束
| 日期 | 反馈内容 | 入档位置 | 触发场景 |
|------|---------|---------|---------|
| YYYY-MM-DD | "保存按钮放底部" | 硬性约束.md 第七节 | UI 调整时 |

## 二、偏好记录
| 日期 | 偏好内容 | 应用范围 |
|------|---------|---------|
| YYYY-MM-DD | 偏好水墨武侠美学 | 所有 UI 设计 |

## 三、纠正记录
| 日期 | AI 判断 | 用户纠正 | 根因 | 防范 |
|------|---------|---------|------|------|
| YYYY-MM-DD | 假设 X 为 Y | 实际为 Z | 凭记忆断言 | 强制 Grep 验证 |
```

### 反馈吸收原则

- **即时入档**：检测到反馈后，在同会话内完成入档，不留尾巴
- **不二次询问**：已入档的反馈不再询问用户「是否要这样」
- **可追溯**：每条规则必须能追溯到用户原始反馈
- **可演化**：用户后续反馈可覆盖或细化已有规则

## 十一、重复错误模式识别（v37 新增）

防止同类错误在多次会话中复发。

### 模式识别机制

AI 在每次任务完成后的 Check 阶段，**额外执行模式识别扫描**：

1. **错误归类**
   - 将本次任务中发现的所有错误归类到固定分类
   - 分类：硬编码 / 幻觉 / 不同步 / 描述错误 / 完整性缺失 / 数值越界 / 边界遗漏

2. **历史检索**
   - 在 `docs/SKILL_RAG.md` 教训库中检索同类历史错误
   - 在 `项目修改记录.md` 中检索同类修复记录

3. **复发判定**
   - 同类错误在近 30 天出现 ≥ 2 次 → 标记为「复发模式」
   - 同类错误在近 7 天出现 ≥ 1 次 → 标记为「高频模式」

4. **进化触发**
   - 复发模式 → 触发第九章自适应规则进化
   - 高频模式 → 在本次任务结束时强化对应触发器

### 模式识别产物

每次模式识别后，在 `docs/SKILL_RAG.md` 的「模式统计」章节更新：

```markdown
## 模式统计（v37 新增）

| 错误类型 | 近 7 天 | 近 30 天 | 复发标记 | 防范规则 |
|---------|---------|----------|---------|---------|
| 硬编码 | 3 | 8 | 复发 | UI_SELF_AUDIT 第二节 |
| 幻觉 | 1 | 4 | 高频 | SELF_LEARNING 第五章 |
| 不同步 | 2 | 5 | 复发 | SELF_LEARNING 第三章 |
```

### 复发处罚

- 复发 ≥ 3 次的错误类型，自动升级为 P0 级约束
- 复发 ≥ 5 次的错误类型，在每次会话启动时强制提醒
- 复发 ≥ 10 次的错误类型，触发项目级复盘，重新评估架构

## 十二、量化学习指标（v37 新增）

用数据衡量自我学习效果，定期评估改进。

### 指标定义

| 指标 | 定义 | 计算方式 | 健康阈值 |
|------|------|---------|---------|
| **错误率** | 单次任务中发现的问题数 / 任务涉及文件数 | `issues / files` | ≤ 1.0 |
| **复发率** | 同类错误在 30 天内复现次数 / 总错误数 | `repeat / total` | ≤ 20% |
| **覆盖率** | 已有规则覆盖的错误类型数 / 总错误类型数 | `covered / all` | ≥ 80% |
| **幻觉率** | 幻觉声明数 / 总声明数 | `hallucinations / claims` | ≤ 5% |
| **反馈吸收率** | 已入档反馈数 / 用户反馈总数 | `archived / feedback` | 100% |
| **规则进化数** | 近 30 天新增/强化的规则数 | `count` | ≥ 3/月 |
| **主动发现率** | AI 主动发现的问题数 / 总问题数 | `proactive / total` | ≥ 70% |

### 指标记录

每次任务完成后，在 `docs/SKILL_RAG.md` 的「学习指标」章节更新：

```markdown
## 学习指标（v37 新增）

### 最近一次任务（YYYY-MM-DD）
- 错误率：0.8 ✓
- 幻觉率：0% ✓
- 主动发现率：85% ✓
- 反馈吸收：1 条

### 30 天累计
- 总任务数：12
- 总错误数：23
- 复发错误数：4（复发率 17%）✓
- 规则进化数：5
- 覆盖率：87% ✓
```

### 指标预警

- 错误率 > 1.5 → 触发架构复盘
- 复发率 > 30% → 触发规则强化
- 幻觉率 > 10% → 触发前置校验强化
- 反馈吸收率 < 100% → 立即补全入档
- 主动发现率 < 50% → 强化会话启动回顾

## 十三、预防性扫描清单（v37 新增）

在用户提问前**主动发现**问题，不等用户提醒。

### 触发条件

AI 在以下场景主动执行预防性扫描：

1. **会话空闲时**：用户长时间未输入，AI 可主动扫描项目状态
2. **任务切换时**：从一类任务切到另一类，先扫描新领域
3. **依赖变更时**：`data.js` / `PIECE_STATS` 等基础常量变更后
4. **新增内容后**：新增角色 / 章节 / 技能 / 机制后
5. **定期自检**：每完成 3 个任务后执行一次全项目扫描

### 预防性扫描清单

| 扫描项 | 扫描方式 | 命中处理 |
|--------|---------|---------|
| HTML 硬编码数字 | Grep `[0-9]+` in index.html | 替换为动态读取 |
| 文档与代码数值不一致 | 比对 docs 与 data.js | 以代码为准同步文档 |
| 技能 desc 与 case 不符 | 比对 data.js 与 skills.js | 同步 desc |
| 新增角色未同步章节 | 检查 STORY_CHAPTERS | 补全章节映射 |
| B王技能数描述错误 | 检查 `${CHARACTERS.bking.actives.length}` | 动态化 |
| 资源版本号未更新 | 检查 index.html ?v=N | 递增版本号 |
| 教程数值过期 | 比对 TUTORIAL_STEPS 与 PIECE_STATS | 同步教程 |
| 难度卡片文案过期 | 检查 syncDifficultyCardsFromData | 重新同步 |
| 修改记录未追加 | 检查 项目修改记录.md | 补充条目 |
| RAG 教训未入档 | 检查本次任务是否产生新教训 | 入档 |

### 主动报告

预防性扫描完成后，若发现问题，AI 应**主动向用户报告**：

```
预防性扫描发现 N 个问题：
1. [P0] index.html 第 75 行硬编码 "20章冒险"，应从 STORY_CHAPTERS.length 读取
2. [P1] data.js 中 PIECE_STATS.k.hp=260 与设计文档 250 不一致
3. [P2] 项目修改记录.md 缺少上次变更的条目

是否立即修复？
```

### 主动报告边界

- 仅报告发现的问题，**不擅自修改**（除非是明显的 P0 级 bug）
- 涉及数值平衡的调整必须先记录到 RAG 待办，由用户确认
- 主动报告产生的改动同样走 PDCA 闭环

## 十四、跨会话知识传递（v37 新增）

确保知识在会话间不丢失。

### 知识传递载体

| 载体 | 用途 | 维护要求 |
|------|------|---------|
| `docs/SKILL_RAG.md` | 教训库 | 每次修改后更新 |
| `docs/USER_FEEDBACK.md` | 用户反馈档案 | 每次反馈后更新 |
| `docs/archive/YYYY-MM/` | 历史教训归档 | 每月 1 日归档 |
| `项目修改记录.md` | 变更日志 | 每次变更后追加 |
| `docs/SKILL_RAG.md` 模式统计 | 错误模式统计 | 每次任务后更新 |
| `docs/SKILL_RAG.md` 学习指标 | 量化指标 | 每次任务后更新 |

### 知识传递流程

```
会话 A 完成
    ↓
更新所有知识载体（教训 / 反馈 / 修改记录 / 指标）
    ↓
归档超期教训到 docs/archive/
    ↓
会话 B 启动
    ↓
执行第八章会话启动回顾
    ↓
读取所有知识载体
    ↓
应用历史教训到本次任务
```

### 归档规则

- `docs/SKILL_RAG.md` 超过 500 行时，将 30 天前的教训归档
- `项目修改记录.md` 超过 1000 行时，将 90 天前的记录归档到 `docs/archive/`
- 归档目录结构：`docs/archive/YYYY-MM/{filename}.archive.md`
- 归档后原文件保留索引指向归档位置

### 知识完整性校验

每周（或每 7 个任务）执行一次知识完整性校验：

- [ ] `docs/SKILL_RAG.md` 教训条目数与归档索引一致
- [ ] `docs/USER_FEEDBACK.md` 反馈条目与 `硬性约束.md` 中的反馈来源一致
- [ ] `项目修改记录.md` 时间戳连续无断层
- [ ] `docs/archive/` 目录结构与索引指向一致
- [ ] 模式统计与实际错误记录一致
